# ADR 0001: гибридный поиск по каталогу в PostgreSQL

**Статус:** принято · **Дата:** 2026-09-30 · **Фаза:** 2

## Контекст

Поиск по каталогу аниме должен:

- находить тайтл по любому названию: русскому, английскому, ромадзи, синонимам;
- переживать опечатки («фрирэн» → «Фрирен») и словоформы («алхимики» → «Стальной алхимик»);
- работать вместе с фильтрами и keyset-пагинацией;
- не требовать отдельного поискового сервиса (Elasticsearch/Meilisearch) на этапе портфолио-проекта.

## Решение

Поиск делает сам PostgreSQL, двумя способами одновременно:

1. **Полнотекстовый** (`tsvector`, GIN): стемминг russian/english, веса — названия A, синонимы B, описание D.
2. **Триграммный** (`pg_trgm`, GIN `gin_trgm_ops`): `q <% search_text` по всем названиям в нижнем регистре.

Условие — `search_vector @@ tsquery OR q <% search_text`, релевантность — `ts_rank_cd + word_similarity`.
Обе колонки `GENERATED ALWAYS … STORED`, их поддерживает сама база, приложение их не пишет.

## Почему не только полнотекстовый

Стеммер Snowball режет имена собственные непредсказуемо:
`to_tsvector('russian', 'титанов')` → `титан`, а `to_tsquery('russian', 'титаны')` → `тита`.
Запрос «титаны» не находит «Атаку титанов». Опечатки FTS не прощает вообще.
Триграммы закрывают оба случая.

## Детали, которые пришлось решить

| Проблема | Решение |
|---|---|
| `array_to_string` — STABLE, а generated-колонкам нужны IMMUTABLE-функции | обёртка `yatoro_array_to_text` (кастомная миграция 0001) |
| Порог `<%` по умолчанию 0,6 отсекает опечатки («фрирэн» ↔ «фрирен» = 0,57) | 0,5 через стартовый параметр соединения `postgres-js`; для PGlite — `SET` (он игнорирует стартовые параметры) |
| При 0,4 проходит шум: `shingeki` → 781 строка, включая «Shinseiki Evangelion» (0,44) | 0,5: 300 строк, все релевантные |
| Функция за `<%` объявлена с `COST 1`: планировщик выбирал Seq Scan (438 мс на 20 тыс. строк) | `ALTER FUNCTION … COST 100` (миграция 0001): BitmapOr по двум GIN-индексам, 5 мс. Без прав владельца миграция не падает, только пишет NOTICE |
| Сортировка по `coalesce(popularity_rank, …)` не использовала индекс по колонке: каждая страница сортировала всю таблицу | expression-индексы ровно под пары `(ключ, id)` из keyset-пагинации |

## Замеры

`bun run bench:catalog` — весь HTTP-путь, 50 прогонов, p95 в мс. База — PGlite (PostgreSQL 18.3 в WASM, однопоточный):
на нативном PostgreSQL CPU-тяжёлые функции (`word_similarity`, `ts_rank_cd`) в разы быстрее.

| Сценарий | 1 000 реальных тайтлов | 20 000 строк* |
|---|---|---|
| Каталог по умолчанию | 4,2 | 4,4 |
| Поиск с опечаткой «фрирэн» | 28,4 | 11,4 |
| «атака титанов» | 31,8 | 25,8 |
| «one piece» | 28,2 | 18,6 |
| `shingeki` | 29,7 | 49,6 |
| Жанры (AND) + сортировка по оценке | 5,6 | 3,9 |
| 10 страниц курсором | 22,8 | 15,9 |

\* 1 000 реальных тайтлов + 19 синтетических копий каждого — пессимистичный случай для поиска (каждое совпадение ×20).

На 1 000 строк планировщик сам выбирает Seq Scan — для нативного Postgres это верно; индексы включаются с ростом таблицы.

## Последствия и ограничения

- Отдельный поисковый сервис не нужен до десятков тысяч тайтлов.
- Запросы, совпадающие с сотнями описаний (`магия` + фильтры: ~88 мс на 20 тыс.), упираются в ранжирование `ts_rank_cd` по длинным текстам.
  Следующий шаг при необходимости — ранжировать по отдельному вектору только из названий.
- Пагинация по релевантности — keyset по округлённому до 6 знаков `numeric`, чтобы значение точно переживало путь через курсор.
