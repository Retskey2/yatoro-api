# ADR 0002: инфраструктура видео-пайплайна — очередь, хранилище, доступ к видео

**Статус:** принято · **Дата:** 2026-10-01 · **Фаза:** 4

## Контекст

Фаза 4: админ загружает серию → воркер перекодирует её ffmpeg в HLS → зритель смотрит в плеере.
Перед кодом нужно выбрать:

1. очередь задач для воркера;
2. S3-совместимое хранилище для локального стека (`docker compose`) и CI;
3. S3-клиент;
4. как браузер загружает файл;
5. как плеер получает доступ к сегментам.

Ограничения: проект работает локально, без хостинга; тесты должны идти без Docker (PGlite).
Все выводы ниже проверены экспериментами — скрипты и результаты в [0002-experiments](0002-experiments/).

## 1. Очередь — pg-boss на PostgreSQL, а не BullMQ + Redis

| | pg-boss (PostgreSQL) | BullMQ + Redis |
|---|---|---|
| Задача ставится в одной транзакции со сменой статуса серии | ✅ откат → 0 задач и 0 строк | ❌ после отката задача **осталась** — нужна outbox-таблица |
| Дополнительный сервис | нет | Redis |
| Тесты без Docker | ✅ работает на PGlite | нужен Redis |
| Подхват новой задачи | ~0,5 с (опрос) | 17 мс (блокирующее ожидание) |
| Повторы с паузой, расписания (cron) | ✅ | ✅ |
| Лицензия | MIT | MIT |

Решающее — атомарность. Без неё возможны «серия в статусе PROCESSING, а задачи нет» или «задача есть, а
транзакция откатилась». У BullMQ это лечится outbox-таблицей и отдельным процессом, который её опрашивает,
то есть очередью в PostgreSQL поверх Redis. Задержка 0,5 с для перекодирования длиной в минуты не важна.

### Цена: адаптер pg-boss → postgres-js + Drizzle

pg-boss рассчитан на драйвер `pg`, у нас postgres-js и Drizzle. Через опцию `db` pg-boss принимает свою функцию
`executeSql`; мы пропускаем его запросы через Drizzle, и `boss.send()` становится частью нашей транзакции.
Эксперимент нашёл четыре несовместимости — каждая получит тест:

| Симптом | Причина | Решение |
|---|---|---|
| `cannot insert multiple commands into a prepared statement` | служебные миграции pg-boss — несколько команд в одном запросе | SQL без параметров — простым протоколом (`.simple()`, в PGlite — `exec`) |
| `UNSAFE_TRANSACTION` | postgres-js не разрешает `BEGIN` на соединении из общего пула | такой SQL — на зарезервированном соединении (`client.reserve()`) |
| `malformed array literal` | Drizzle разворачивает массив в `${…}` в список `($1, $2…)` | `sql.param(value)` — массив уходит одним параметром |
| задача после ошибки «висит» в `active` и не повторяется | `pg` сам сериализует объекты в JSON, postgres-js — нет; запрос «отметить как неудачную» падал | обычные объекты → `JSON.stringify` |

Последний случай — самый коварный: ошибка обработчика не роняет воркер, а тихо оставляет задачу в `active`
до истечения таймаута (по умолчанию 15 минут).

## 2. Хранилище — SeaweedFS, а не MinIO

MinIO, заложенный в исходный план, больше не подходит (проверено 01.10.2026):
репозиторий `minio/minio` в архиве («THIS REPOSITORY IS NO LONGER MAINTAINED»),
community-версия распространяется только исходниками, образ `minio/minio` на Docker Hub удалён (404).

RustFS и SeaweedFS прошли одинаковый набор проверок — **оба прошли всё**:

- создание бакета и CORS; запись и чтение; загрузка и скачивание по подписанной ссылке;
  частичное чтение (`Range` → 206, нужно HLS-плееру); серверная загрузка по частям;
- CORS preflight для нашего origin — разрешён, для чужого — 403;
- подделанная подпись, подпись от другого файла, истёкшая ссылка, анонимное чтение — 403.

Выбран **SeaweedFS**: стабильные релизы (4.48 от 28.09.2026), проект с 2014 года.
У RustFS из последних 100 релизов стабильный один, остальные — preview.
Garage не проверялся: ему нужна ручная настройка раскладки кластера и ключей — лишние шаги для стека «одной командой».
Минус SeaweedFS: учётные данные S3 задаются файлом конфигурации, а не переменными окружения.

## 3. S3-клиент — встроенный `Bun.S3Client`, AWS SDK только для настройки бакета

`Bun.S3Client` покрывает весь путь данных: подписанные ссылки GET/PUT, серверная загрузка по частям (`writer`),
`Range`. Подпись ссылки — локальное HMAC-вычисление, **~6 мкс**.
Чего в нём нет: создания бакета и настройки CORS, подписанных ссылок на части multipart-загрузки.
AWS SDK (`@aws-sdk/client-s3`) используется только в одноразовой инициализации бакета.

## 4. Загрузка из браузера — одна подписанная PUT-ссылка

Файл идёт прямо в хранилище, API его не читает. Это закрывает A11 из аудита: сейчас `/media/videos`
держит до 100 МБ в памяти и разбирает тело запроса до проверки прав.

- Ограничение S3 — до 5 ГБ на один PUT; серии обычно меньше 2 ГБ.
- Нет докачки при обрыве связи.
- Путь развития: multipart из браузера с подписанными ссылками на части (AWS SDK `UploadPartCommand` + presigner).

## 5. Доступ к видео — приватный бакет и подпись плейлиста

Бакет приватный. API отдаёт HLS-плейлисты, заменяя пути сегментов подписанными ссылками;
сами сегменты идут прямо из хранилища, мимо API.
При ~6 мкс на подпись плейлист из 500 сегментов подписывается примерно за 3 мс.

| Вариант | Контроль доступа | Нагрузка на API |
|---|---|---|
| **Подпись плейлиста** (выбран) | ✅ можно проверять пользователя | только плейлисты (килобайты) |
| Публичный префикс с неугадываемыми путями | ❌ | нет |
| Проксирование сегментов через API | ✅ | весь видеотрафик |

Компромисс: подписанную ссылку можно переслать, пока она действует. Срок жизни — порядка длительности просмотра
(несколько часов): VOD-плеер загружает плейлист один раз.

## Последствия

- Redis в стеке не нужен; `docker compose`: PostgreSQL, SeaweedFS, API, воркер.
- Адаптер pg-boss — отдельный модуль с тестами на каждую из четырёх особенностей.
- `/media/videos` удаляется после появления загрузки по подписанной ссылке.
- Расписание pg-boss (`schedule`) закрывает отложенный пункт фазы 2 — регулярное обновление онгоингов.
